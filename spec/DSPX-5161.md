# xtest: add a headless-browser "web" SDK backend alongside the Node js CLI

## Summary
Whyweb-sdk exists to run in browsers, but xtest only exercises it through the Node CLI (@opentdf/ctl, xtest/sdk/js/cli.sh). That hides browser-only behaviour and surfaces Node-only bugs as if they were SDK bugs. The current example is DSPX-5160: Node's fs.openAsBlob truncates file-backed Blob sizes to 32 bits, so the js CLI cannot decrypt any TDF of 4 GiB or more. Browsers handle the same file correctly. In a probe on 2026-10-14, Chromium, Firefox and WebKit (via Playwright) all returned the exact size of a 64 GiB TDF from <input type=file>, and slice(-1000) returned the real ZIP tail.
Add a new, separate SDK flavour, web, that runs web-sdk inside a headless browser. Keep the existing Node js backend. The CLI is a shipped product, and both paths need coverage.
Designxtest/sdk/web/cli.sh. Same contract as the other shims: encrypt|decrypt <src> <dst> <fmt>, supports <feature>, and the XT_WITH_* env vars. It runs a small Node Playwright driver.
The driver:
Launches headless Chromium. Firefox and WebKit are optional later; see DSPX-5084.
Serves a static page containing web-sdk's browser bundle.
Passes the input with setInputFiles. Playwright hands the browser the file by path, so nothing is copied, even at 64 GiB.
Runs encrypt/decrypt in the page with client-credentials auth.
Streams the output back out.
Output sink. Do not reuse the web-app's StreamSaver/download path. It is Chromium-only in practice: WebKit buffers the whole output as a Blob, and Firefox took the CI runner down at 4 GiB (DSPX-5084). Instead the page pipes its output ReadableStream as chunked POSTs to a localhost sink served by the driver. That works in every engine, and the sink writes to <dst> or discards (so /dev/null works for the --bench-scale benchmark).
CORS. Page-to-platform (:8080) and page-to-Keycloak (:8888) calls are cross-origin. The driver's server should reverse-proxy them the way the web-app's Vite proxy does, so CORS is still exercised. Do not use --disable-web-security.
xtest wiring:
Add web to sdk_type in xtest/tdfs.py, plus SDK_NAMES in perf/config.py and the conftest --sdks parsing.
supports can largely reuse the js shim's checks, since it is the same library and version.
Version the backend by web-sdk lib version.
otdf-sdk-mgr. Install web from a release or from source (tip --ref): build the browser bundle and stage the driver and its Playwright browser.
CI. Add the web flavour to the xtest.yml matrix. Playwright browsers need caching.
Acceptanceuv run pytest test_tdfs.py --sdks "go web js" passes the cross-SDK roundtrips with web on both the encrypt and decrypt sides.
--bench --bench-scale 64GiB --sdks "go java js web" (from the opentdf/tests --bench-scale mode) measures web decrypts of go/java TDFs at 64 GiB. Encrypting with web at 64 GiB still hits GLOBAL_BYTE_LIMIT until DSPX-4652 lands.
The Node js backend is unchanged and still runs.
NotesThe benchmark process tree now includes Chromium. Startup of about 1 s is negligible at multi-GiB sizes, and peak RSS will reflect the renderer.
Related: DSPX-5160 (Node openAsBlob truncation), DSPX-5084 (Firefox large-file CI), DSPX-4648 / DSPX-4652 (web-sdk large-file limits), DSPX-4886 (xtest terabyte-size tests).

## Problem / Motivation
xtest reaches web-sdk only through its Node CLI, so Node-only bugs (DSPX-5160)
look like SDK bugs, and browser-only behaviour goes untested.

## Proposed Solution (as built)
A new `web` SDK flavour next to `js`, which is unchanged.

- `xtest/sdk/web/cli.sh`: the same contract as the other shims. `supports`
  answers from `features.json`, which the install step writes from the bundled
  library (version, tdfSpecVersion, PUBLIC_KEY_ALGORITHMS), so a probe never
  launches a browser.
- `xtest/sdk/web/driver/`: `driver.mjs` (Node + Playwright), `page.js`
  (bundled with `@opentdf/sdk` by esbuild in `build.mjs`), and `index.html`.
  The driver serves the page on `127.0.0.1:<ephemeral>` and attaches the input
  with `setInputFiles`. The page runs the job with client-credentials auth and
  POSTs the output back.
- Output sink: offset-tagged chunked POSTs, at most 4 x 4 MiB in flight,
  written positionally to `<dst>` (or discarded for `/dev/null`). No
  StreamSaver/download path.
- `xtest/sdk/web/stage.sh`: assembles a dist dir from any `@opentdf/sdk` npm
  spec or tarball, in a scratch directory renamed into place last.
- otdf-sdk-mgr: `web` is in `ALL_SDKS`, not `DEFAULT_SDKS`. Release installs use
  npm `@opentdf/sdk`. Source installs reuse the js worktree
  (`SDK_SOURCE_ALIASES`) and `xtest/sdk/web/Makefile`.
- CI (xct job): `make -C xtest/sdk/web from-js` stages `web` for every
  installed js version. `web` then decrypts in every cell, and the matrix
  gains `web@<tag>` encrypt entries.

### Refinement: only Keycloak is proxied
The ticket asked for platform (:8080) and Keycloak (:8888) to be
reverse-proxied. Only Keycloak is (`/__kc/`, with Host rewritten so `iss` stays
correct). Its dev clients send no CORS headers on the token endpoint, and
client-credentials in a browser is test scaffolding anyway.

The platform and KAS are called directly, cross-origin, and rely on the
platform's `server.cors` config (dev default: any origin). A proxy would change
what is tested: the KAS URL the SDK uses is the URL it writes into each KAO.
Proxied KAS URLs would be baked into web-encrypted TDFs, so go and java could
not decrypt them, and decrypt has to reach the arbitrary KAS URLs a TDF names.
Calling direct also exercises the platform's CORS for real. Web security is
never disabled.

## Inputs / Outputs / Contracts
- `cli.sh encrypt|decrypt <src> <dst> <fmt>`, `cli.sh supports <feature>`.
- Honoured: XT_WITH_ATTRIBUTES, _ASSERTIONS, _ASSERTION_VERIFICATION_KEYS,
  _MIME_TYPE, _TARGET_MODE, _ECWRAP, _VERIFY_ASSERTIONS, _KAS_ALLOWLIST (also
  the legacy _KAS_ALLOW_LIST spelling the other shims read),
  _IGNORE_KAS_ALLOWLIST; CLIENTID/CLIENTSECRET/PLATFORMURL/KASURL/KCFULLURL.
- Rejected with an error: XT_WITH_DPOP, _ECDSA_BINDING, _PLAINTEXT_POLICY.
- Driver knobs: XT_WEB_BROWSER, XT_WEB_HEADED, XT_WEB_DEBUG.

## Edge Cases & Constraints
- Failures print the error name, message and cause chain, so xtest's tamper
  and KAS-error regexes match. A failed run deletes any partial `<dst>`.
- Encrypt above GLOBAL_BYTE_LIMIT fails until DSPX-4652.
- Under `--bench`, the process tree includes Chromium.

## Out of Scope
- Firefox/WebKit in CI (the driver supports them via XT_WEB_BROWSER).
- DPoP in the web driver.
- The `--bench-scale` mode itself (separate change). `web` is in
  `perf/config.SDK_NAMES` and in the standard SDK enumeration, so it will be
  picked up once that lands.
- bench/zip64 CI jobs, and the `focus-sdk` input.
