# NFS front end so SDK CLIs read sparse TDFs as local files

## Summary
Epic DSPX-4886 tests 100 GiB–50 TiB TDFs by keeping only the bytes a planned
read needs, in the DSPX-5111 extent store behind a loopback HTTP Range server
(#653). Rather than teach every SDK CLI to read URLs, present the store as an
ordinary local file through a small user-space NFSv3 server and a kernel
mount. All three CLIs already read local files at random offsets.

## Proposed Solution
- `xtest/nfsserve/`: a Go server (go-nfs) exporting one read-only file.
  Each NFS READ is one Range GET to the range server, so the retention plan,
  extent store and request log are reused. Works with `FullFile` too.
- A GET answered 410 (dropped extent) reads as filler, the repeating
  non-zero `DROPPED!` aligned to offset 0, and is in the range server's log.
  An error would not do: the kernel rounds application reads out to whole
  NFS READs (a 16-byte buffered read became ~1 MiB in the spike), and EIO
  there fails the read of kept bytes too. AES-GCM still rejects filler.
- `retention_plan(..., pad=)` widens kept extents up to `data_end` and
  keeps the bytes just before it; the store keeps the tail from `data_end`,
  java's trailing empty segment included. `nfsmount.PAD` (2 MiB) is twice
  what a READ holding planned bytes can reach past them: one 1 MiB rsize.
  1 MiB READs ran 2.5x faster than 64 KiB ones on macOS.
- Mounts are soft. macOS: `mount_nfs`, no sudo, read-ahead off (it still
  reads whole rsize blocks). Linux: `sudo mount -t nfs`, needing
  nfs-common, with `read_ahead_kb` one rsize: at 0 it issues a 4 KiB READ
  per page, which ran a 4.5 GiB js encrypt past a 150-minute timeout.

## Inputs / Outputs / Contracts
- Fixture `nfs_mount(source, name="payload.tdf") -> (path, request_log)`:
  any number per test, each a range server plus a mount. Teardown unmounts
  and stops nfsserve before the range server joins its handlers.
- `nfsmount.mounted(url, root, binary)` yields `Mount(file, server)`;
  always unmounts (forcing if needed) and stops the server.
- Mount points are `<XT_TMP_DIR>/nfs/<pid>.<suffix>`; the session fixture
  reaps those whose process has gone.
- The server exits when its stdin closes, so it dies with a killed run.
- Skips if the host cannot mount (no Go, no `mount.nfs`, no passwordless
  sudo on Linux); `XT_NFS_REQUIRED=1` makes that a failure, as in CI.

## Out of Scope
Partial decrypt through the mount and sparse SDK cells (DSPX-5544);
regenerating dropped segments (DSPX-5547).

## Acceptance Criteria
- [x] macOS without sudo and `ubuntu-latest`, no SDK: kept ranges read
  byte-identical, dropped ranges read as filler, every fetch is logged;
  offsets above 2^32 and 2^40; logical sizes 100 GiB, 5 TiB, 50 TiB
  (`test_nfsmount_units.py`, in check.yml). A sparse copy of the java
  golden with a trailing empty segment opens and reads to its last byte.
- [x] A real SDK CLI decrypts a small TDF through the mount in full-file
  mode (`test_nfsmount.py`, in X-Test's standard runs).
- [x] No mounts or server processes left after a failed or killed run.
- [x] Runs in CI on `ubuntu-latest`.
