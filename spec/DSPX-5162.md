# web-sdk CLI: evaluate Bun and Deno as alternatives to Node for large-file support

## Summary
WhyThe web-sdk CLI (@opentdf/ctl) runs on Node, and Node's fs.openAsBlob truncates file-backed Blob sizes to 32 bits (DSPX-5160, upstream nodejs/node#66207). As a result the CLI cannot decrypt TDFs of 4 GiB or more. Browsers are not affected; see DSPX-5161 for a headless-browser backend. Before choosing how the CLI should read files, find out whether Bun or Deno avoid the problem and whether either is a credible runtime for the CLI. That could be an interim fix, or a documented supported alternative.
ScopeFor Bun and Deno (current stable releases), next to Node 24 as the baseline:
File Blob correctness above 4 GiB.
Bun: Bun.file(path) size, slice(-N) and slice(start, end) at offsets above 2^32.
Deno: whether it has a file-backed Blob at all, and its node:fs openAsBlob compat behaviour.
Both: the runtime's node:fs openAsBlob compatibility shim, since the CLI calls that today.
Use the 64 GiB go-written TDF from the opentdf/tests --bench-scale run, or a sparse file with known tail bytes. A probe for this was started on 2026-10-15 but interrupted before it produced results.
Running the existing CLI unmodified. Can @opentdf/ctl encrypt and decrypt under each runtime (Bun's Node compat; deno run npm:@opentdf/ctl or a compiled binary)? Record every compat gap (node: APIs, Web Streams, crypto, fetch/HTTP2, the connect-rpc client).
Large-file behaviour. A 64 GiB decrypt of go/java TDFs to /dev/null, with wall time, throughput, CPU time and peak RSS. Measure with the xtest --bench-scale harness by pointing a copy of xtest/sdk/js/cli.sh at the alternative runtime.
Operational fit. Install and distribution story (npm, single-file bun build --compile / deno compile binaries), CI availability, and licence and support posture.
Out of scopeChanging the shipped CLI's runtime. This task produces a comparison and a recommendation only.
The position-based Node file chunker prototyped under DSPX-5160, which is the Node-side fix and is compared against here.
DeliverableA short write-up (spec doc or comment here) with a results table for Node, Bun and Deno, plus a recommendation: stay on Node with the DSPX-5160 chunker, offer Bun/Deno as supported alternatives, or switch.
Related: DSPX-5160, DSPX-5161, DSPX-4648.

## Problem / Motivation
Node's `openAsBlob` truncates file Blob sizes mod 2^32, so `@opentdf/ctl`
cannot decrypt TDFs >= 4 GiB. Before committing to a Node-side fix, check
whether Bun or Deno avoid the problem and could run the CLI.

## Proposed Solution
Comparison and recommendation only. The full write-up and results tables are
in opentdf/web-sdk `spec/DSPX-5162-bun-deno.md` (same branch). In short: stay
on Node with the DSPX-5160 chunker plus bounded decrypt prefetch; treat Bun
as best-effort; do not offer Deno.

This repo adds the reusable affordance that made the comparison possible:
`XT_JS_RUNTIME` (or a per-dist `.js-runtime` file) selects the runtime that
`xtest/sdk/js/cli.sh` runs the JS CLI under.

## Inputs / Outputs / Contracts
- `XT_JS_RUNTIME=node|bun|deno`. Default: the contents of
  `xtest/sdk/js/dist/<v>/.js-runtime`, else `node`. Unknown values exit 2.
- `node` keeps the historical `npx @opentdf/ctl` path. `bun` and `deno` run
  `node_modules/.bin/opentdf` directly; `deno` runs with `-A`.

## Edge Cases & Constraints
- `bunx` without `--bun` follows the CLI's `#!/usr/bin/env node` shebang and
  runs Node, so the shim calls `bun <bin>` instead.
- Released CLIs (<= 0.20.0) fail every decrypt under Bun because of a Bun
  `Blob.slice(-n)` quirk; the SDK fix is in the web-sdk PR. Deno's
  `openAsBlob` buffers the whole input in memory.

## Out of Scope
Changing the shipped CLI runtime; the DSPX-5160 chunker; CI jobs for Bun or
Deno.
