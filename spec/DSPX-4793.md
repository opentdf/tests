# upstream(opentdf/tests): make xtest a buildable distribution (src layout, build-system, package data)

## Summary

Turn `xtest/` from a run-in-place test directory into an installable
distribution, so downstream consumers can depend on it instead of vendoring it.
Steps B1–B3 of DSPX-4640.

Today `xtest/pyproject.toml` has no `[build-system]` table, and says so in a
comment at `xtest/pyproject.toml:59`: *"This is a test suite, not a
distributable package. Use `uv pip install -r pyproject.toml` or `uv sync` for
dependencies."* There is nothing to `uv add`. Four downstream repos want to run
the cross-SDK suite against their own platform build, and every one of them has
to vendor the whole repository — submodule or subtree — and invoke pytest with
`cwd == xtest/`, because the suite reads `sdk/...`, `manifest.schema.json`,
`extra-keys.json` and `golden/` as paths relative to the process working
directory.

The pattern to copy is already in the repo: the two sibling tools,
`otdf-sdk-mgr` and `otdf-local`, are properly packaged —
`build-backend = "uv_build"` (`otdf-sdk-mgr/pyproject.toml:24-26`), `src/`
layout, `[project.scripts]`.

| step | what it does | risk |
|---|---|---|
| B1 | `src/xtest/` layout, `[build-system]`, `pytest11` plugin, license fix | mechanical; largest diff |
| B2 | `XT_SDK_DIR`/`--sdk-dir`; no filesystem probes at import time | behavioural, small |
| B3 | data files under `src/xtest/data/`, read via `importlib.resources` | behavioural, small |

All three landed together. `XT_ENV_FILE` did not — see [Out of
Scope](#out-of-scope).

## Problem / Motivation

The suite is not installable, and four distinct properties conspire to keep it
that way. Fixing any three of them leaves it still not installable.

**1. There is no build backend.** No `[build-system]` table, so `uv build`
fails and `uv add xtest @ ...` has nothing to invoke. This is the headline, and
it is also the least interesting of the four: adding six lines of TOML makes
`uv build` emit a wheel that does not work.

**2. The layout puts a bare `conftest` at the site-packages root.** Every
module lives flat at the top of `xtest/` — `tdfs.py`, `abac.py`, `conftest.py`,
`test_*.py` — with `__init__.py` only under `fixtures/` and `perf/`. Installed
as-is, `conftest.py` lands at `site-packages/conftest.py`. pytest's default
`importmode=prepend` derives a module name from the basename, so the consumer's
own `conftest.py` and the installed one both want to be the top-level module
`conftest`, and the second one collected raises `ImportPathMismatchError`. The
same applies to every unqualified `test_*.py` and to generic names like
`sizes`, `assertions`, `audit_logs`. The flat layout is not a style preference
here; it is the install blocker.

`[tool.ruff.lint.isort] known-first-party` is the tell — it enumerates eight
top-level names (`xtest/pyproject.toml:84-93`) precisely because there is no
package to name instead. (DSPX-4640 says nine; the file has eight.)

**3. Relative paths are resolved against the process working directory, some
of them at import time.**

| site | code | effect |
|---|---|---|
| `xtest/tdfs.py:671` | `self.path = f"sdk/{sdk}/dist/{version}/cli.sh"` | every CLI invocation needs `cwd == xtest/` |
| `xtest/tdfs.py:947-948` | `sdk_path = os.path.join("sdk", sdk, "dist")` | version discovery silently finds nothing elsewhere |
| `xtest/otdfctl.py:55` | `path = otdfctl_path if otdfctl_path else "sdk/go/otdfctl.sh"` | same, for the admin CLI |
| `xtest/conftest.py:669-692` | `load_otdfctl()`, called at module scope on line 692 | probes `sdk/go/dist/main/otdfctl.sh` **while conftest is being imported** |

The last row is the sharp edge: a filesystem probe during collection setup
cannot be configured, cannot be skipped, and turns "no SDKs built here" into a
collection error rather than a deselection. `xtest/test_self.py:8` does the same
thing at module scope (`otdfctl = OpentdfCommandLineTool()`), which means merely
*importing* that test module in an environment with no `sdk/` tree aborts the
session.

Note what is **not** in this table: `xtest/tdfs.py:240`
(`FORCED_SUPPORTS = _parse_forced_supports(os.environ.get("XT_FORCE_SUPPORTS", ""))`)
reads an environment variable at import time, which is fine — no filesystem, no
cwd, and the value cannot change mid-session.

**4. Data files are opened by bare relative name.**

| file | read from | today |
|---|---|---|
| `manifest.schema.json` | `xtest/tdfs.py:632` `validate_manifest_schema` | requires the `SCHEMA_FILE` env var; CI sets it in four places (`.github/workflows/xtest.yml:637,649,1029,1328`) |
| `extra-keys.json` | `xtest/fixtures/keys.py:126` | `Path("extra-keys.json")` — cwd-relative |
| `golden/*.tdf` | `xtest/test_legacy.py:9-11` | `xtest_dir / "golden" / name` |

`extra-keys.json` has a second, cross-package consumer:
`otdf-local/src/otdf_local/utils/keys.py:176` reaches into
`xtest_root / "xtest" / "extra-keys.json"` and, two lines later,
`return []` if it is missing. Move the file without fixing that and the
platform comes up with no extra keys and no error.

Finally, `xtest/pyproject.toml:7` declares `license = { text = "BSD-3-Clause" }`
while the repository `LICENSE` is BSD-3-Clause-**Clear** — a different licence,
which withholds patent rights. Harmless while nothing is published; wrong the
moment a wheel with that metadata exists.

## Proposed Solution

### B1 — `src/xtest/` layout and a build backend

Move every module under `src/xtest/`, add `__init__.py`, and put the test
modules in their own subpackage:

```
xtest/
├── pyproject.toml              # + [build-system] uv_build, + [project.entry-points.pytest11]
└── src/xtest/
    ├── __init__.py
    ├── abac.py assertions.py audit_logs.py otdfctl.py sizes.py tdfs.py zipinspect.py
    ├── paths.py                # NEW — XT_SDK_DIR resolution
    ├── plugin.py               # was conftest.py
    ├── fixtures/  perf/
    ├── data/                   # manifest.schema.json, extra-keys.json, golden/
    └── tests/                  # test_*.py + __init__.py
```

`tests/` ships in the wheel deliberately: running the suite *is* the reason a
consumer installs this, and `pytest --pyargs xtest.tests` is the whole
interface. With `tests/__init__.py` present, the modules import as
`xtest.tests.test_tdfs` rather than as top-level `test_tdfs`, which is what
makes them coexist with a consumer's own `test_tdfs.py`.

**`conftest.py` becomes `plugin.py`, registered as a `pytest11` entry point.**
This is the one part of B1 that is not a pure move, and it is not optional. A
`conftest.py` inside an installed package is only loaded if pytest happens to
collect through that directory, and — critically — it is loaded *after* the
command line has been parsed, so its `pytest_addoption` never runs. The suite
has ~20 options. An entry-point plugin is loaded during startup, before
argument parsing, which is exactly the hook `pytest_addoption` requires:

```toml
[project.entry-points.pytest11]
xtest = "xtest.plugin"
```

`-p no:xtest` disables it, which is the standard escape hatch and better than
what a `conftest.py` offers (nothing). The `pytest_plugins` list inside the
module gains the `xtest.` prefix on all eight fixture modules.

*Rejected: keep `conftest.py` and tell consumers to `-p xtest.conftest`.* It
works, but it makes every consumer's invocation carry a flag that exists only
because we picked the wrong file name, and it does not fix the
`site-packages/conftest.py` collision — the file is still there, still named
`conftest`.

*Rejected: `packages = ["xtest"]` with a flat layout (no `src/`).* Avoids the
move, but keeps the repo root on `sys.path` during test runs, which is the
mechanism by which a flat layout tests the source tree instead of the installed
artifact. The point of this ticket is that the installed artifact works; a
layout that cannot tell the difference cannot verify it. Both siblings already
use `src/`.

`known-first-party` collapses from eight names to `["xtest"]`. License becomes
the SPDX expression `BSD-3-Clause-Clear` (PEP 639 string form, which
`uv_build` accepts).

`requires = ["uv_build>=0.11.19,<0.13"]` — the upper bound deviates from the
siblings, which pin only a lower bound. uv itself warns about the missing
bound during `uv build`; a build backend is exactly the dependency where an
unbounded major is a bad idea.

### B2 — remove the cwd coupling

A new `xtest/paths.py` owns the one question "where is the SDK tree":

```python
SDK_DIR_ENV = "XT_SDK_DIR"
DEFAULT_SDK_DIR = "sdk"

def sdk_dir() -> Path:
    return Path(os.environ.get(SDK_DIR_ENV) or DEFAULT_SDK_DIR)
```

The value is **read on every call and never captured at import**. That is the
whole design: a module-level `SDK_DIR = ...` reintroduces the bug in a new
place, because `plugin.pytest_configure` resolves `--sdk-dir` after the
modules have already been imported.

Precedence is `--sdk-dir` > `XT_SDK_DIR` > `./sdk`, decided once in
`_configure_sdk_dir(config)` during `pytest_configure`, which writes the result
back into `os.environ` so that the subprocesses the suite spawns see the same
answer. The default is unchanged, so an in-tree run behaves exactly as before.

The import-time probe goes away:

```python
@functools.cache
def _otdfctl_tool() -> OpentdfCommandLineTool:
    ...
    return load_otdfctl()

@pytest.fixture(scope="module")
def otdfctl():
    return _otdfctl_tool()
```

`functools.cache` preserves the old "resolve once per session" behaviour while
moving the resolution to first use. `test_self.py`'s four tests take the
existing module-scoped `otdfctl` fixture instead of constructing the tool at
module scope. Absent an SDK tree the suite now logs
`no SDK distributions under sdk; only tests that need no SDK will run` at DEBUG
and deselects, rather than erroring during collection.

Markers move out of `[tool.pytest.ini_options]` and into
`plugin.pytest_configure` via `config.addinivalue_line("markers", ...)`. The
ini table is only read from the session's rootdir — which stops being this
directory the moment a consumer installs the wheel and runs from their own
repo, at which point all four markers (`benchmark`, `no_audit_logs`, `zip64`,
`slow`) emit `PytestUnknownMarkWarning`. Registering from the plugin is the
only placement that travels with the distribution.

### B3 — package data

`manifest.schema.json`, `extra-keys.json` and `golden/*.tdf` move to
`src/xtest/data/`, with an `__init__.py` that resolves them through
`importlib.resources`:

```python
def data_path(*parts: str) -> Path:
    ref = files(__name__).joinpath(*parts)
    if not isinstance(ref, Path):
        raise RuntimeError(...)
    return ref
```

Three named accessors (`manifest_schema_file()`, `extra_keys_file()`,
`golden_file(name)`) sit on top, so no caller writes a literal filename twice.

`test.env` is deliberately **not** shipped: it is generated per environment and
carries credentials. It has no accessor here at all.

`setup-cli-tool/action.yaml` is a composite GitHub Action. Actions are
resolved by repository path, not from a Python wheel, so it stays at the repo
root and is out of scope for packaging by construction.

`SCHEMA_FILE` degrades from *mandatory* to *override*:

```python
schema_file_path = os.getenv("SCHEMA_FILE") or str(data.manifest_schema_file())
```

which lets the four `SCHEMA_FILE: "manifest.schema.json"` lines come out of
`xtest.yml` while leaving the variable available to anyone pointing the
validator at a candidate schema.

## Inputs / Outputs / Contracts

```
--sdk-dir <path>               # pytest option; highest precedence
XT_SDK_DIR=<path>              # env var; default ./sdk
SCHEMA_FILE=<path>             # optional override; was mandatory
```

```python
# xtest/paths.py
SDK_DIR_ENV: str = "XT_SDK_DIR"
DEFAULT_SDK_DIR: str = "sdk"
def sdk_dir() -> Path: ...

# xtest/data/__init__.py
def data_path(*parts: str) -> Path: ...
def golden_file(name: str) -> Path: ...
def manifest_schema_file() -> Path: ...
def extra_keys_file() -> Path: ...
```

Distribution contract:

| | |
|---|---|
| name / version | `xtest` 0.1.0 (unchanged) |
| backend | `uv_build>=0.11.19,<0.13` |
| entry point | `pytest11: xtest = "xtest.plugin"` |
| consumer invocation | `pytest --pyargs xtest.tests` |
| opt out | `-p no:xtest` |
| licence | `BSD-3-Clause-Clear` |

Unchanged on purpose: every existing option, env var and marker keeps its
name and default, and an in-tree `uv run pytest` from `xtest/` behaves as it
did. The four repos pinning `opentdf/tests@main` need no change.

## Edge Cases & Constraints

**The wheel is 10.2 MB, and 10.0 MiB of that is one file.** `golden/` is 9
members and essentially all of the payload is
`big-java-4.3.0-e0f8caf.tdf` (10 489 161 bytes). Every consumer pays that on
every install even though only `test_legacy.py` reads it. Splitting the corpus
into an `xtest-golden` extra was considered and rejected for this slice: it
doubles the release surface to fix a problem nobody has reported, and it is a
reversible decision. Worth revisiting if the corpus grows. (Practical note for
anyone reproducing this: jj's default `snapshot.max-new-file-size` is 1 MiB and
will silently refuse to snapshot that file when it moves, producing a delete
with no matching add. Raise it before committing.)

**`importlib.resources.files()` returns a `Traversable`, not a `Path`.** The
callers pass these to `subprocess`, to `open()`, and to CLI shims — all of
which want a real filesystem path. `data_path()` therefore asserts
`isinstance(ref, Path)` and raises a diagnostic naming zipimport rather than
letting a `Traversable` leak into a subprocess argv and fail somewhere
unhelpful. Wheels are unpacked on install, so this holds in every supported
configuration; the check exists to make the unsupported one legible.

**`sdk/go/cli.sh:174` still works, and was not touched.** It walks up looking
for a `pyproject.toml` containing `name = "xtest"`:

```sh
if [ -f "$XTEST_DIR/pyproject.toml" ] && grep -q 'name = "xtest"' "$XTEST_DIR/pyproject.toml"; then
```

`xtest/pyproject.toml` keeps that line and `sdk/` stays at the `xtest/` root,
so the walk-up resolves as before. Removing the shell-side coupling is
DSPX-4791/DSPX-4792's job, and touching `cli.sh` here would collide with them.

**`otdf-local` reads `extra-keys.json` across the package boundary and fails
silently.** `otdf-local/src/otdf_local/utils/keys.py:176` is updated to the new
path. This is the one change outside `xtest/` that is load-bearing rather than
cosmetic, because the failure mode is `return []` — a platform that starts
successfully with the wrong key set.

**Markers cannot be registered from `pyproject.toml` once installed** — see
B2. This was found by the out-of-tree gate, which emitted four
`PytestUnknownMarkWarning`s that an in-tree run never shows.

**The pytest11 plugin loads in every environment that installs xtest**,
including ones where the consumer never intends to run the suite. It registers
options and markers and imports `xtest.plugin`'s module-level dependencies;
after B2 it performs no I/O at import. That is the reason the `functools.cache`
change is a hard requirement of this ticket rather than a nicety — an
import-time filesystem probe in an always-loaded plugin would break unrelated
test suites in the consumer's repo.

**Two tests are deselected by default** in the out-of-tree collection (335 of
337). Same as in-tree; not a packaging artifact.

## Out of Scope

- **`XT_ENV_FILE` (part of B2 as written in DSPX-4640).** Deferred, deliberately.
  Its only consumers are `sdk/{go,java,js}/cli.sh` and `sdk/go/otdfctl.sh`,
  which this ticket must not touch (DSPX-4791/DSPX-4792). A Python-side
  accessor that nothing reads is dead code, and exporting a resolved
  `XT_ENV_FILE` into the subprocess environment would change the env dict that
  the 18 argv/env assertions in `test_sdk_commands.py` pin. It belongs with the
  shell-side work.
- **Entry-point registries for `container_type` / `sdk_type` / `feature_type`**
  (B4). That is DSPX-4794; the `Literal`s at `xtest/tdfs.py:103,112,117` and
  `sdk_specs_opt` at `xtest/conftest.py:345` are untouched here.
- **`otdf-adapter/` and any change to `sdk/*/cli.sh`.** DSPX-4791 and
  DSPX-4792.
- **Publishing to an index.** This produces a wheel; nothing tags, signs or
  uploads it. Consumers install from a path or a VCS reference.
- **`setup-cli-tool/action.yaml`.** A composite Action cannot live in a wheel.
- **Renaming the `xtest/` directory** or changing the distribution name or
  version. Both would break the four pinned consumers for no benefit in this
  slice.
