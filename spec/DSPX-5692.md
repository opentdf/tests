# xtest: cover strict DPoP htu with configured trusted origins (server.auth.dpop.htu.origins / strict)

## Summary
Whyopentdf/platform#4326 (DSPX-4707) adds server.auth.dpop.htu.origins, the public HTTP(S) origins that clients sign in full-URL DPoP proofs, and server.auth.dpop.htu.strict, which requires configured origins and rejects path-only proofs. The deprecated strict_htu setting keeps working. Only Go unit tests cover this today: service/internal/auth/dpop_htu_origins_test.go and service/pkg/config/dpop_htu_test.go.
xtest doesn't exercise it at all:
Nothing in opentdf/tests sets htu.origins, strict or strict_htu. The platform startup action used by xtest.yml only offers dpop-challenge-enabled.
On the PR platform lanes (bootstrap-ref: pqc-enabled, Keycloak 25.0), Keycloak issues Bearer tokens. With no cnf claim and enforceDPoP off, checkToken returns before validateDPoP runs (service/internal/auth/authn.go). So test_dpop_happy_path_roundtrip passes without any proof or htu being checked.
The negative tests (test_dpop_rejects_tampered_proof_htu and others) skip with "Keycloak realm not configured for DPoP (token_type='Bearer')".
I found this in the platform-xtest run on opentdf/platform#4326 (xct (pull-4326, go@pull-4326), 2026-11-17).
ScopeAdd a way to start the xtest platform with server.auth.dpop.htu.origins and server.auth.dpop.htu.strict: an input on the startup action, or a platform config overlay. Run it in a lane whose Keycloak issues DPoP-bound tokens; that prerequisite is DSPX-5642.
Add cross-SDK cases (go, java, and js once web-sdk#991/#993 ship) in strict mode with a configured origin:
An SDK roundtrip whose proofs are signed for the configured public origin passes.
A proof whose htu uses a different origin, with the same path, is rejected.
A path-only htu proof is rejected.
Optional: with origins configured and strict off, path-only proofs are still accepted (compatibility mode).
Optional: the deprecated strict_htu: true with no origins still enforces request-origin matching.
Acceptance criteriaThe new cases run in xtest CI, and the logs show they actually ran rather than skipped (see DSPX-4333 / opentdf/tests#695).
A platform build without these settings is gated out by a capability check, not failed.
RelatedDSPX-4707: the feature under test (opentdf/platform#4326, stacked on #4325).
DSPX-4706: path-only compatibility and cross-origin replay, the risk strict mode closes.
DSPX-5642: blocked by it, for a Keycloak lane that issues DPoP-bound tokens with DPoP tests not skipped.
DSPX-4333: DPoP capability skips made visible.

## Problem / Motivation
Strict htu and the origin allowlist close cross-origin proof replay (DSPX-4706), but only Go unit tests cover them. Nothing in xtest configures them, so an SDK that signs path-only or wrong-origin proofs would not be caught.

## Proposed Solution
- Base on opentdf/tests#695 (DSPX-4333), which owns `test_dpop.py`'s skip plumbing (`CapabilityGap`, realm check).
- `tdfs.py`: a platform-only feature `dpop_htu_origins`, present when the well-known config has `dpop.htu_origins` (the DSPX-5635 contract). `PlatformFeatureSet.dpop_htu_origins` holds the list. The mode isn't advertised, so `dpop_htu_strict` comes from the last `dpop htu matching` line in the platform log.
- `test_dpop.py`: target the platform's own KAS (PLATFORMURL), the only server CI configures:
  - strict SDK roundtrip;
  - an unconfigured origin with the same path is rejected; the request's own origin (via 127.0.0.1) is rejected when not configured; a configured origin is accepted through that alias;
  - path-only htu, strict and compatibility mode: DSPX-5642's `test_dpop_proof_shapes_across_versions` covers it once `dpop_htu_forms()` returns `{"url"}` under strict.
  The HTTP-level cases encrypt with the Bearer client so SDK htu handling can't fail them. SDKs that sign path-only proofs (legacy builds) xfail the strict roundtrip rather than fail it.
- `xtest.yml`: DSPX-5642's "Choose the DPoP lane" step also picks the htu settings. Strict runs on the `main` platform lane of the weekly cron, or when the `dpop-htu-strict` input is set, passing `OPENTDF_SERVER_AUTH_DPOP_HTU_STRICT=true` and `..._ORIGINS=http://localhost:8080` as step env on the main platform startup (the action has no input for them). Nightly and PR lanes stay in compatibility mode so the legacy-SDK cells keep testing path-only proofs against current platforms.

## Inputs / Outputs / Contracts
- Well-known: `dpop.htu_origins: list[str]` (normalized; `[]` when unset).
- Log: JSON record `msg="dpop htu matching"`, `strict: bool`, `origins: list`.
- Env: `OPENTDF_SERVER_AUTH_DPOP_HTU_STRICT`, `OPENTDF_SERVER_AUTH_DPOP_HTU_ORIGINS` (comma-separated).

## Edge Cases & Constraints
- Platforms without #4326 ignore the env vars; the `dpop_htu_origins` gate skips as a capability gap.
- No platform log, or a text-format one: the mode is unknown, and the strict cases skip with that reason.
- In strict mode, path-only SDKs xfail the DPoP roundtrips (DSPX-5528); an XPASS means they changed.
- KAS-only instances (alpha…) keep request-derived origins; they don't run well-known, so a negotiating SDK (#4322) signs path-only proofs there.

## Out of Scope
- Deprecated `strict_htu` with no origins (would need a second platform config).
- A DPoP Keycloak on every lane, and legacy-SDK runs (DSPX-5642, the base of this stack).

## Acceptance Criteria
- [ ] On the weekly main lane (or with `dpop-htu-strict`), with #4326 merged, the htu cases run (not listed under capability gaps).
- [ ] On a platform without the settings, they skip through the `dpop_htu_origins` gate.
