# bounded streaming harness for large SDK operations

## Summary

Test I/O for the 100 GiB, 5 TiB and 50 TiB TDF tests (epic DSPX-4886): exercise
an SDK CLI's encrypt and decrypt without the plaintext, ciphertext or decrypted
output ever being stored in full. `xtest/streamharness.py`; live controls in
`xtest/test_streaming.py`, opt-in via `--stream`.

## Problem / Motivation

`tdfs.SDK.encrypt`/`decrypt` take paths and buffer the CLI's stdout and stderr
in memory. `pt_file` writes the whole plaintext, and its line format breaks at
~931 GiB (DSPX-4735). Three full copies of a 100 GiB payload do not fit on a
runner, and the larger tiers do not fit on any disk we have.

## Proposed Solution

- **Generator.** `Plaintext(length)` is an AES-128-CTR keystream with the block
  index as counter, so `(offset, length) -> bytes` costs only what it returns,
  ~13 GB/s locally. It is also a `rangeserve.Source`, so `rangeserve.serve`
  can serve it and DSPX-5543 can mount it as a seekable file.
- **Input adapters.** A FIFO fed from the generator, or a regular file: a
  mount (`mount=` hook, for DSPX-5543) when given, else a materialised copy in
  scratch.
- **Output adapters.** A FIFO drained into a consumer, or a regular file
  replayed into it after exit. A CLI that renames over its output FIFO is
  reported; one that seeks fails with ESPIPE and is reported unsupported.
- **`CountedSink`.** Counts bytes, keeps a rolling tail (`tail_ceiling`;
  `ManifestTooLarge` above it), and at close parses the ZIP64 end records,
  central directory and manifest with `zipinspect.read_central_directory()`
  into `TdfEvidence`: sizes, entry offsets, and a `ManifestSummary` whose
  per-segment array is reduced to counts and a size histogram. Checks that the
  manifest and `0.payload` account for exactly the plaintext sent. Every byte
  goes, before `write` returns, to an optional downstream `write()`/`close()`
  consumer: `SparseSink` for DSPX-5545 (whose kept tail is then parsed in
  place of a second buffer), `FileSink` for the controls.
- **`Validator`.** Compares decrypted output with the generator by position and
  demands the exact length.
- **`run()`.** One CLI invocation through `perf/_launcher.py`, so peak RSS and
  wall time come from the same `wait4` reading as the benchmarks. Bounded
  stdout/stderr capture. FIFO opens never block: ENXIO polling on the write
  side, O_NONBLOCK until a writer appears on the read side. The CLI's `TMPDIR`
  and `java.io.tmpdir` point into scratch, which a sampler measures against
  the `Budget`. A consumer or producer error, or an interrupt, SIGTERMs the
  launcher, which now kills the measured process group on SIGTERM or SIGINT as
  it does on timeout, with both held off across the fork.
- **`probe()`.** Tries routes most-streaming first (fifo→fifo, file→fifo,
  fifo→file, file→file) until one streams. Each rung after the first keeps an
  end proven by an earlier one, so the first that works attributes the
  failures. A route that only succeeds by copying at least half its input to
  `TMPDIR` is "spooled", not streaming. Only a refusal (non-zero exit, early
  EOF, timeout) marks a route unsupported: a route the CLI accepts and gets
  wrong fails the probe, and so does a CLI that no route works for.

## Inputs / Outputs / Contracts

For DSPX-5545:

```python
pt = Plaintext(100 << 30)                  # pt(offset, n) is DSPX-5547's callable
layout = dict(payload_start=p0, plaintext_length=pt.length, segment_size=seg)
plan = retention_plan(ranges, **layout)
sink = CountedSink(downstream=SparseSink(store_dir, plan, tail_ceiling=c, **layout),
                   plaintext_length=pt.length)
r = streamharness.run(sdk_cmd, src=FifoInput(pt), dst=FifoOutput(sink),
                      scratch=scratch, budget=Budget.from_env())
r.result                 # TdfEvidence, parsed from the store's tail
sink.downstream_result   # the ExtentStore
```

With a `SparseSink` downstream, `CountedSink` keeps no tail of its own and
parses the store through `SourceReader`, so there is one ceiling-sized buffer,
not two. The layout must match the route being run: go writes a ZIP64 local
header when it cannot measure its input (the FIFO route), so `p0` is 59 there
rather than 39. Each run's `TdfEvidence.payload_start` reports it, the probe
summary prints it for the chosen encrypt, and `SparseSink` rejects a mismatch
within the first 64 KiB.

Or `encrypt(cmd, pt, route=..., downstream=...)` and
`decrypt(cmd, ct_path, pt, n, route=...)`, with routes from `probe(...)`.
`cmd(src, dst) -> (argv, env)` is `tdfs.SDK.encrypt_command` /
`decrypt_command` with `container` bound.

Pytest: `--stream chunky` (5 MiB, every PR, in `xct`), `--stream medium`
(2.1 GiB, nightly, in the `zip64` job). `XT_STREAM_TIMEOUT`,
`XT_STREAM_MAX_RSS` and `XT_STREAM_MAX_SCRATCH` set the budget.

## Per-SDK results

From #698's X-Test run, 5 MiB probe; identical on the platform main and
v0.30.0 lanes. The job summaries have the full tables.

| SDK | encrypt | decrypt | needs DSPX-5543 at scale |
|---|---|---|---|
| go@main, go@v0.41.0 | fifo → fifo, streams | fifo input accepted but spooled 5 MiB to `TMPDIR`; file → fifo streams | decrypt input |
| java@main, java@v0.19.1 | fifo → fifo, streams | fifo refused (`InvalidZipException`: no EOCD); file → fifo streams | decrypt input |
| js@main, js@v0.4.0 | fifo refused (not a regular file); file → fifo streams | fifo refused; file → fifo streams | encrypt and decrypt input |

Every output end streams through a FIFO. No CLI decrypts from a pipe without
copying it first, since the central directory comes last; at scale the input is
a seekable mount.

## Edge Cases & Constraints

- Peak RSS is the largest single process in the CLI's tree (`wait4`), as in
  `perf/measure.py`, not the sum over the tree.
- A CLI that stops reading within one pipe buffer (~64 KiB) of the end looks
  like a complete read from the input side. The manifest length check and the
  validator catch the result.
- Scratch is apparent file size under the scratch root, sampled every 50 ms.
- `rangeserve`'s HTTP server manages ~360-920 MiB/s at the 64 KiB NFS rsize
  of #696 (DSPX-5543), so a mounted `Plaintext` is fine at 100 GiB but takes
  about a day for a full 50 TiB read.

## Out of Scope

- The DSPX-5543 mount itself, and SDK-API adapters. A CLI that needs a seekable
  input uses a materialised file at control sizes, and is reported as needing
  the mount above them.
- Regenerating dropped segments (DSPX-5547) and the capacity tests (DSPX-5545).

## Acceptance Criteria

- [x] Go, Java, JS: the harness records whether each CLI streams through each
  route, or reports the route unsupported with the reason (table above).
- [x] 5 MiB control: exact byte counts both ways, manifest and ZIP structure
  checked, output validated by position. Runs on every PR.
- [ ] 2.1 GiB control without three full copies: wired into the nightly
  `zip64` job, not yet run in CI.
- [x] Short input, sink failure, wrong byte count, child failure, timeout,
  early EOF and an interrupted run raise without leaving the CLI running
  (`test_streamharness_units.py`, in `check.yml`).
- [x] No size added to the `pt_file`/`--sizes` fanout. `--stream` is opt-in,
  and a `--stream` run with no passing control fails.
