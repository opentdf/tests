# xtest pqc and hybrid pq/t tests skipped or not skipped correctly

## Summary
Make sure the tests are run if all components could support them.

`test_pqc.py` has six cells per encrypt/decrypt pair: X-Wing, X-Wing + EC,
`hpqt:secp256r1-mlkem768`, `hpqt:secp384r1-mlkem1024`, `mlkem:768`,
`mlkem:1024`. A cell should run whenever the platform (km1), otdfctl (to
register the key) and the *encrypt* SDK can all handle the algorithm. The
decrypt SDK needs nothing: KAS unwraps the PQ KAO and rewraps for the client's
RSA/EC session key, which is why the decrypt side is deliberately not gated.

## Problem / Motivation

Audit of the scheduled X-Test run on main, 2026-10-20 (run 39383110889), and
the previous night's (39213990689) for the go release lane:

| encrypt SDK                | X-Wing | X-Wing+EC | secp+ML-KEM 3/5 | ML-KEM 768/1024 |
|----------------------------|--------|-----------|-----------------|-----------------|
| go@main, go@v0.38.1        | runs   | runs      | runs            | runs            |
| java@main, java@v0.19.1    | runs   | runs      | runs            | runs            |
| js@main                    | skip   | skip      | skip            | runs            |
| js "latest" (= ctl@0.4.0)  | skip   | skip      | skip            | skip            |

Every non-js skip is legitimate (released-only pairs, or `ecwrap` missing on
the js@v0.4.0 decrypt side of X-Wing+EC). The platform side is fine: km1's log
reports `mechanism-xwing`, `mechanism-secpmlkem` and `mechanism-mlkem` on both
the `main` and `v0.29.0` lanes.

What is wrong:

1. **js "latest" is not the latest release.** `SDK_TAG_INFIXES["js"] = "sdk"`
   makes `versions resolve js latest` consider only `sdk/vX.Y.Z` tags. web-sdk
   switched to release-please's `sdk-vX.Y.Z` at 0.4.1, so `latest` has been
   pinned to `sdk/v0.4.0` ever since, and CI installs `@opentdf/ctl@0.4.0`.
   That build predates `key_management`, so it skips every PQ cell -- and most
   of `test_abac.py` -- not because of PQ at all. The real latest is
   `sdk-v0.22.0`, which supports ML-KEM (added in 0.21.0, web-sdk#933).

2. **The newest js CLI on npm is older than the newest js SDK.** Even with (1)
   fixed, `@opentdf/ctl@0.22.0` cannot be installed from npm: web-sdk's
   *Deliver Client to npm registry* job failed on the `sdk-v0.21.0` and
   `sdk-v0.22.0` releases (`You cannot publish over the previously published
   versions: 0.22.0` from the `@opentdf/sdk` step), which aborts before
   `@opentdf/ctl` is published. npm `latest` for `@opentdf/ctl` is still
   0.20.0, which has no ML-KEM.

3. **The js shim has no `mechanism-secpmlkem` case.** It falls through to
   `Unknown feature` (exit 2), which `SDK.supports` reads as "no". The answer
   is right today but only by accident, and the shims' own convention is to be
   explicit so that a typo cannot pass for a known-missing feature. It also
   means nothing will turn the cell on when web-sdk gains support.

4. **web-sdk does not support the hybrids yet.** At both main and
   `sdk-v0.22.0`, web-sdk writes `wrapped`, `ec-wrapped` and `mlkem-wrapped`
   KAOs only, so the js@main hybrid skips are correct. web-sdk#1049 (open)
   adds `hybrid-wrapped` for `hpqt:secp256r1-mlkem768` and
   `hpqt:secp384r1-mlkem1024`, and adds both to `KEY_ALGORITHMS`, so they will
   appear in the CLI's `--encapKeyType` choices. It explicitly does not cover
   X-Wing.

Not a problem, though it looks like one: on 2026-10-20 the matrix had no
`go@v0.39.0` lane. `versions resolve` drops a ref whose SHA it has already
emitted, and platform `main` was still the `otdfctl 0.39.0` release commit
(e1afd30b), so `latest` and `main` were the same build.

## Proposed Solution

1. **js shim (`xtest/sdk/js/cli.sh`).** Add an explicit `mechanism-secpmlkem`
   case that greps `opentdf help` for `hpqt:secp256r1-mlkem768`, mirroring the
   java probe. Tighten `mechanism-xwing` to grep `hpqt:xwing`. Both answer
   "no" today and turn on, with no change here, once web-sdk ships the
   algorithm identifiers in its CLI choices.

2. **js `latest` resolution (`otdf-sdk-mgr`).** Accept both the `sdk/` and
   `sdk-` tag forms for js, so `latest` is `sdk-v0.22.0`, and report the tag
   as git names it in `release`. Because that CLI is not on npm,
   `install_js_release` falls back when `@opentdf/ctl@<v>` is missing: it
   builds `cli/` from the tag checkout against the published
   `@opentdf/sdk@<v>`, the way java release CLIs are built against Maven
   Central (#652). `install stable js` follows the same release tag. The
   alternative -- resolve `latest` from the npm dist-tag -- is simpler but
   tests ctl 0.20.0, which has no ML-KEM, so js "latest" would cover nothing
   new from PQ until web-sdk fixes its delivery job.

   In `xtest.yml`, gate the js `make` on `setup-cli-tool`'s `needs-build`
   output, as java already does, rather than on "has a head". Otherwise a js
   release that falls back to a source checkout is never built when no js
   head is in the run.

3. **Upstream (web-sdk), not in this repo:**
   - delivery job: publish `@opentdf/ctl` even when `@opentdf/sdk` is
     already on npm, and backfill 0.21.0 / 0.22.0 (DSPX-5277; does not block
     this work);
   - land web-sdk#1049 for the secp hybrids;
   - decide whether X-Wing is in scope for web-sdk (no ticket or PR found).

4. **Optional regression guard.** The zip64 job already fails when a green
   job ran nothing (`xtest.yml`, "A green job whose tests were all
   skipped..."). A similar check could assert that, on PQ-enabled lanes, the
   go and java encrypt cells in `test_pqc.py` all executed, so a broken probe
   cannot quietly turn PQ coverage into skips again.

## Inputs / Outputs / Contracts

- `xtest/sdk/js/cli.sh supports mechanism-secpmlkem` -- exit 0 iff the CLI's
  help lists `hpqt:secp256r1-mlkem768`; exit 1 otherwise (never 2).
- `xtest/sdk/js/cli.sh supports mechanism-xwing` -- exit 0 iff help lists
  `hpqt:xwing`.
- `otdf-sdk-mgr versions resolve js latest` -- returns the newest
  `sdk-vX.Y.Z` (or legacy `sdk/vX.Y.Z`) release, `release: "sdk-v0.22.0"`
  today.
- `otdf-sdk-mgr install release js:<v>` -- succeeds for releases whose CLI is
  not on npm.

## Edge Cases & Constraints

- `--rewrapKeyType` shares web-sdk's algorithm list, so a help-text match does
  not by itself prove decrypt-side support. That is acceptable because only
  the encrypt side is gated.
- Evaluate web-sdk#1049 before it merges with
  `otdf-sdk-mgr install tip --ref pr:1049 js`. The new probe should already
  answer yes for that build; `XT_FORCE_SUPPORTS=mechanism-secpmlkem` is the
  fallback if it does not.
- Platform lanes older than v0.17 start KAS without PQ (`pqc-check` in
  `xtest.yml`). The km1 log then lacks the mechanisms and the cells skip on the
  platform gate, which is correct.
- `latest` and `main` sharing a SHA drops the `latest` lane. That is
  intended.

## Out of Scope

- The X-Wing implementation in web-sdk.
- `mechanism-rsa-4096` (no js shim case; falls through to `Unknown feature`)
  and `mechanism-ec-curves-384-521` (hard-coded `False` for js in
  `tdfs.SDK._uncached_supports`). Both skip `test_abac.py`'s extended
  mechanism cells for js@main. Same class of bug, but not PQ.
- Principled key/config assembly in `start-up-with-containers` (DSPX-3992).

## Acceptance Criteria
- [ ] No PQ feature reaches the `Unknown feature` branch of any `sdk/*/cli.sh`.
- [ ] `otdf-sdk-mgr versions resolve js latest` returns `sdk-v0.22.0` (or
      newer), and the X-Test matrix installs and runs that build.
- [ ] On the scheduled X-Test run, for go and java at both main and latest,
      all six `test_pqc.py` cells run on both platform lanes.
- [ ] js@main and js@latest run both ML-KEM cells. Their hybrid cells skip with
      a `mechanism-xwing` / `mechanism-secpmlkem` reason.
- [ ] When web-sdk#1049 merges, js@main's secp+ML-KEM cells run with no
      further change in this repo.
