# regenerate dropped segments so full decrypts need no stored ciphertext

## Summary

Let a reader decrypt a whole 100 GiB–50 TiB TDF (epic DSPX-4886) without the
ciphertext ever being stored. The sparse sink (DSPX-5111) keeps the ZIP head
and tail; this keeps each segment's IV and tag too, and rebuilds every dropped
segment on read from the DEK and the plaintext generator. That gives
DSPX-5109/5110 a reader source without S3.

## Problem / Motivation

A partial decrypt needs only a few segments, so a sparse store suffices. A
full decrypt reads every segment, and storing 50 TiB of ciphertext is not an
option. AES-GCM output is fixed by the key, the IV and the plaintext, and
xtest's plaintext is deterministic, so the ciphertext can be recomputed
instead of kept, given the DEK.

## Part 1 (this PR)

Everything provable at small scale, in `xtest/regenerate.py`:

- `SegmentRecorder` takes the same in-order `write` calls as `SparseSink`
  (which is unchanged) and records every segment's 12-byte IV and 16-byte tag
  into two flat files. 28 bytes a segment on disk, nothing per segment in
  memory. Layout comes from `payload_start`, `segment_size` and
  `plaintext_length`, as for `retention_plan`; it also records the 28 bytes
  after the last data segment, because java appends an empty segment when the
  plaintext is a whole number of segments.
- `unwrap_dek` opens each key split with an RSA KAS private-key PEM
  (RSA-OAEP, SHA-1 digest and MGF1, as the KAS and all three SDKs use) and
  XORs the splits. KAOs sharing a split id are alternatives. `ec-wrapped`
  raises `KeyUnavailable`.
- `RegeneratingSource` implements the range server's `Source`: kept extents
  as stored, other segments as `IV || AES-GCM(DEK, IV, plaintext) || tag`. It
  refuses to build unless the recorded tags equal the manifest's segment
  hashes and the root signature verifies under the DEK. A regenerated tag that
  differs from the recorded one raises before the segment is returned.
- The plaintext generator is an `(offset, length) -> bytes` callable, to be
  replaced by DSPX-5108's canonical generator.

Tests:

- `test_regenerate_units.py` (offline, in `check.yml`): a synthetic,
  really-encrypted TDF with two key splits, most segments dropped, is
  byte-identical over every range across segment, IV and tag edges, and over
  HTTP; a wrong DEK or IV raises. The java golden TDF regenerates from its
  golden key, covering legacy hex hashes and the trailing empty segment.
- `test_regenerate.py` (X-Test): the 5 MiB TDF from each encrypting SDK,
  DEK unwrapped with `$PLATFORM_DIR/kas-private.pem`, served whole through
  the range server, must be byte-identical. Skips if that file is absent.

## Constraints

- Needs the KAS private key on disk: otdf-local's and CI's file-based keys,
  not key management or an HSM.
- Regeneration costs about as much CPU as the decrypt. Move it into Go if
  that binds.
- The manifest is parsed whole, per segment. Fine at 100 GiB (51,200
  segments); at 50 TiB (26 M segments, a 2.6 GB manifest) the tag check
  needs a streaming parse.

## Deferred

- DSPX-5108: the streaming harness that feeds a real SDK's output into the
  sink and recorder, supplies the plaintext generator, and runs the 100 GiB
  full decrypt with a disk bound, which the ticket's full acceptance
  criteria need.
- DSPX-5543: mounting the source as a local file over NFS, so SDK CLIs that
  cannot read HTTP decrypt from it.
- `ec-wrapped` and post-quantum KAOs.

## Acceptance Criteria (part 1)

- [x] Dropped segments regenerate byte-identically from DEK, IV and plaintext.
- [x] A wrong DEK or IV raises; mismatched bytes are never returned.
- [x] DEK unwrap from RSA KAOs with several splits.
- [x] E2E against each SDK's real output in X-Test, or a visible skip.
- [ ] 100 GiB full decrypt through the mount within a disk bound (DSPX-5108).
