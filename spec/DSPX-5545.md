# sparse-backed partial decrypt at 100 GiB through the NFS mount

## Summary

A scheduled X-Test job encrypts 100 GiB + 112 KiB of generated plaintext once
per SDK into a store that keeps only the extents a planned set of partial reads needs,
plus the ZIP tail. Every SDK then partially decrypts each planned range from an
NFS mount of that store, as an ordinary seekable file. It is DSPX-5118 with the
DSPX-5543 mount in place of HTTP, so no reader needs URL input.

## Problem / Motivation

Partial decrypt is meant for TDFs far larger than a test runner's disk. The
per-PR cells (DSPX-5117, DSPX-5544) use 5-20 MiB TDFs, so nothing checks a
reader at the offsets and manifest sizes where 32-bit arithmetic and ZIP64
handling break, or that a reader fetches only what it needs from a 100 GiB
file.

## Proposed Solution

`xtest/test_sparse_partial_decrypt.py`, collected only under `--sparse SIZE`
(`fixtures/sparse.py`):

1. **Probe.** `stream_probe` (DSPX-5108) picks each encrypting SDK's route at
   5 MiB. Its TDF gives the route's `payload_start` and the SDK's segment
   size, so the plan is in the right ciphertext offsets.
2. **Plan, before encrypt.** Plaintext ranges: the first segment, the last
   segment, a range across a segment boundary mid-file, ranges across 2^32
   and 2^36 when the size reaches them, and four seeded random ranges. The
   seed is random unless `--sparse-seed` is given, and is reported. Each range
   is widened as the reader will read it (web-sdk also reads the preceding
   segment of a last-segment read, DSPX-5219) and turned into ciphertext
   extents with `retention_plan(..., pad=nfsmount.PAD)`.
   The default size is 100 GiB + 112 KiB so go and js end on a real short
   segment and java writes no trailing empty one; the exact-multiple case,
   where web-sdk mishandles java's empty segment (DSPX-5551, web-sdk#1134),
   is covered per PR by `test_partial_decrypt_whole_segments`.
3. **Encrypt once per SDK.** `streamharness.encrypt` feeds `Plaintext` to the
   CLI (a FIFO, or for js a mount of the generator) and streams the TDF into
   a `SparseSink`, which keeps the planned extents, checks the layout and ZIP64
   structure, and keeps the tail. `CountedSink` checks the byte count and
   manifest against the plaintext length. Scratch is capped while the CLI runs.
4. **Partial decrypt.** For each encrypter, decrypter and range, a fresh NFS
   mount of the store, `--offset/--length` through `XT_WITH_PLAINTEXT_RANGE`,
   and the output checked against the generator by position.
5. **Fetch bound.** Dropped extents read as filler, so success alone does not
   show the reader stayed in the plan. The bytes every NFS READ asked for,
   filler included, must fit `fetch_budget` with the NFS source's RSIZE
   alignment and 3 MiB allowance, the per-PR bound from DSPX-5544.
6. **Report.** Per encrypt: SDK, route, payload start, segment size and count,
   manifest bytes, wall time, throughput, peak RSS, retained bytes, peak disk
   against its bound. Per decrypt: range, wall time, peak RSS, bytes fetched
   against the bound, filler READs, peak disk against its bound. Written to
   the job summary and `test-results/sparse-partial-decrypt.json`.

The `sparse` job in `.github/workflows/xtest.yml` runs this on one
`ubuntu-latest` runner, SDKs in turn, weekly (`0 18 * * 0`) and on dispatch.
It installs only the first ref of each `*-ref` input (main by default), since
every further build would be another full-size encrypt.

## Inputs / Outputs / Contracts

- pytest: `--sparse SIZE`, `--sparse-segment-size SIZE`,
  `--sparse-timeout SECONDS` (per encrypt), `--sparse-seed INT`,
  `--sparse-report PATH`; SDKs from `--sdks-encrypt` / `--sdks-decrypt`.
- Workflow dispatch: `sparse-size` (runs the job when set), `sparse-only`
  (skip the functional matrix; size defaults to `100GiB+112KiB`; sizes may
  be sums), `sparse-sdks`,
  `sparse-segment-size`, `sparse-timeout-minutes` (job timeout, 45-360; each
  encrypt gets all but 30 minutes).
- New capability `encrypt_over_64gb`, required above 64e9 bytes: go yes; java
  from 0.19.0 (java-sdk#393 removed a 2^36 cap); js no (web-sdk
  `GLOBAL_BYTE_LIMIT` is 64e9, WS-9363). `XT_FORCE_SUPPORTS` can force it.
- `test_partial_decrypt.fetch_budget` takes a `Layout` (payload start and
  end, TDF length, segment count) rather than a file, so a store can use it;
  `read_extent` holds the DSPX-5219 widening both use.

## Edge Cases & Constraints

- No CLI can set the segment size. `--sparse-segment-size` is a requirement;
  an SDK whose default differs skips, labelled.
- A route whose `payload_start` or segment size differs at full size from the
  probe's fails: the sink checks the first local header within the first
  64 KiB, and the segment layout at close.
- Java appends an empty segment after a whole number of segments. The plan
  keeps the DSPX-5219 widening for the last data segment whichever count the
  TDF ends up with; the fetch bound uses the manifest's count.
- Disk: encrypt is bounded by plan + manifest + 16 MiB, decrypt by store +
  range + 16 MiB. Both are asserted; the encrypt bound minus the manifest is
  also enforced while the CLI runs.
- The tail is held in memory until the TDF ends: `max(64 MiB, 256 B per
  segment)`. That is ~6.7 GB at 50 TiB with 2 MiB segments, which DSPX-5546
  has to plan for.

## Out of Scope

- Full decrypts of the sparse TDF (DSPX-5547 regenerates dropped segments for
  that).
- 5 TiB and 50 TiB runs (DSPX-5546). The job takes the size and timeout as
  inputs; at those sizes one encrypt can take hours, so run one SDK per
  dispatch or split the job by SDK.
- Partial decrypt over HTTP (DSPX-5118).

## Acceptance Criteria

- [x] Runs weekly within one standard runner's disk and time budget.
- [x] At least one real encrypt and one real partial decrypt per selected SDK,
      where the SDK can: go cannot decrypt a range until platform#4229/#4234
      land in otdfctl, and js cannot encrypt over 64e9 bytes. Both show as
      labelled skips.
- [x] Skips and unsupported capabilities are visible in the summary and JSON;
      a run with no passing encrypt or no passing decrypt fails.
- [x] Size, SDKs, segment size and timeout are parameters.
- [x] Peak local disk is bounded by manifest + retained segments + a fixed
      overhead, and asserted.
- [x] Reported as partial-read capability, not as a full decrypt.

- Every java@main and js@main partial decrypt passed at both sizes,
  js<-java included. Highest fetched/bound at 100 GiB was 0.78 (last
  segment, java->js: 8.4 of 13.0 MiB), with no filler READs. go decrypts
  skip until platform#4229/#4234.
- At 4.5 GiB + 112 KiB: go encrypts in 13 s (360 MiB/s), java in 18 s
  (254 MiB/s), js in 28 s (167 MiB/s, file route through the mounted
  generator; 2.5 h before #696's read-ahead fix). Peak disk ~48 of 64 MiB.
- Local macOS runs at 256 MiB and 4.5 GiB with real SDKs found DSPX-5551:
  at exact multiples of the segment size js reads java's TDFs from segment
  0. Fixed by web-sdk#1134 and covered per PR by #655's
  `test_partial_decrypt_whole_segments`, which is the only failure in the
  java xct cells on this PR until #1134 merges.
