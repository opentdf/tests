# upstream(opentdf/tests): otdf-adapter package — typed protocol + SubprocessCliAdapter

## Summary
Blocked by DSPX-4640. Upstream work in github.com/opentdf/tests.
Step A1 of replacing the bash cli.sh shims with a typed Python adapter layer. Behaviour-identical by construction — this ticket lands the abstraction with a single implementation that still shells out to cli.sh.
WhyThe current stack is four layers, two of them lossy:
test body → tdfs.SDK.encrypt(...)            typed Python
          → XT_WITH_* env dict               lossy: every option becomes a string
          → cli.sh <verb> <src> <dst> <fmt>  lossy: four positional slots, nowhere for options
          → bash rebuilds argv               per-SDK flag vocabulary, in shell, three times
          → otdfctl / java -jar / npxXT_WITH_* exists only because cli.sh <verb> <src> <dst> <fmt> has four positional slots and nowhere to put options. It is a workaround for a bad signature, not a design.
846 lines of shell across sdk/{go,java,js}/cli.sh, of which ~360 are supports case statements: hand-rolled semver in awk (--version --json | jq -re .sdk_version | awk -F. '{ if ($1 > 0 || ($1 == 0 && $2 >= 12)) exit 0; ... }', repeated ~15 times with divergent expressions), help decrypt | grep --kas-allowlist probes, or a hardcoded exit 0/exit 1.
And the migration is already half-done: tdfs._uncached_supports (tdfs.py:894) opens with a Python match carrying 10 hardcoded SDK/feature answers that override the shell, falling through to subprocess.check_call([cli.sh, "supports", feature]) only at the end. One of its own comments says the quiet part: "go and java answer this from their own cli.sh supports case statement, which is in this repo, not theirs." One concept, two languages.
ScopeNew package otdf-adapter/, sibling of otdf-sdk-mgr and otdf-local — copy their shape exactly (build-backend = "uv_build", src/ layout, [project.scripts]).
otdf-adapter/
├── pyproject.toml              # [project.entry-points."otdf.adapters"] go/java/js
└── src/otdf_adapter/
    ├── protocol.py             # SdkAdapter Protocol + request dataclasses
    ├── gates.py                # declarative feature gates + one evaluator
    ├── registry.py             # entry-point discovery -> load_adapter(name, version, dist_dir)
    ├── subprocess_cli.py       # shared argv build / run / logging / error mapping
    └── descriptor.py           # reads dist/<version>/adapter.jsonTyped requests replace XT_WITH_*:
@dataclass(frozen=True)
class EncryptRequest:
    src: Path; dst: Path
    container: str = "ztdf"
    mime_type: str | None = "application/octet-stream"
    attributes: Sequence[str] = ()
    assertions: str | None = None
    target_mode: str | None = None
    policy_mode: Literal["encrypted", "plaintext"] = "encrypted"
    ecwrap: bool = False
    ecdsa_binding: bool = False

class SdkAdapter(Protocol):
    name: str
    def encrypt(self, r: EncryptRequest) -> Path: ...
    def decrypt(self, r: DecryptRequest) -> Path: ...
    def supports(self, feature: str, container: str = "ztdf") -> bool: ...
    def version(self) -> SdkVersion: ...Note supports takes a container — today's cli.sh supports <feature> cannot express "supports assertions for ztdf but not for format X".
Gate kinds for gates.py (used by the follow-up ticket, defined here): MinVersion (via packaging.version or the in-tree otdf_sdk_mgr.semver), HelpContains, Always, Delegate (the SDK answers natively — java already ships cmdline.jar supports dpop), Unprobeable(reason).
The only implementation landed here is SubprocessCliAdapter, whose encrypt/decrypt/supports build the same argv and XT_WITH_* env as today and exec the existing cli.sh. tdfs.SDK delegates to it. No shell is deleted.
